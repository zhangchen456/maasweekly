# AR-02：API 加载、查询与限流

状态：DONE_LOCAL / PRODUCTION_PENDING（45/45回归通过；线上代理链/环境切换待发布验收）。优先级：P1。依赖：AR-01。

## 目标与范围

同版本无需重复解析，数据加载不长时间阻塞在线请求，常用查询使用索引，不同访客不会共享一个很小的应用配额。保留 REST/MCP 同查询语义、完整性校验和 cursor 固定版本。

分 2A/2B/2C 三个可独立验证的变更交付，避免一次同时改变加载、查询和流量行为。入口：`services/agent-api/src/`、相关 tests、`ops/maas-agent.env.example`、Nginx 配置生成逻辑及 API/MCP 契约。

## 2A. 数据加载与缓存

1. 在轮询入口先读取最小 manifest 元数据，比较 datasetVersion；相同版本不读取或解析业务集合。明确返回 `changed/unchanged/failed`，避免把跳过误报为成功重载。
2. 核实生产槽位的数据根固定到不可变 release 后，在该模式关闭周期轮询；本地可变数据根继续支持轮询与 SIGHUP。先核实真实环境配置，不仅修改 env 示例。
3. 新版与历史版使用同一完整校验链：schemaVersion、版本/路径、文件清单、bytes/hash、必要结构与引用检查。启动、首次历史版本读取、版本切换都必须校验。
4. 将文件读取、hash、JSON 解析及索引构建移出在线事件循环的长任务。异步 readFile 只解决 I/O，仍需测量 JSON.parse/hash/对象传输；根据 AR-01 结果采用 worker 或其他隔离方案。
5. 同一版本的并发加载复用一个进行中任务。用加载序号或候选版本复查防止较慢的旧任务覆盖已就绪的新版本；构建成功后一次替换 current，失败保留旧版。
6. 历史 Dataset 缓存采用有界 LRU/内存预算，current 不被淘汰；正在执行的请求持有自己的对象引用。版本仍在保留期时，内存淘汰后可从磁盘再次加载，不能返回“已过期”。
7. 不可变文件在运行期不靠重复解析监测篡改；启动/加载完整校验与运维完整性审计承担此职责。保留显式重新校验入口，确定 SIGHUP 的强制校验语义并写入文档。

测试覆盖：同版本跳过；坏 manifest/hash 拒载；无有效数据时 503；新版加载失败续服旧版；新旧加载完成顺序倒置；历史版本同时首次请求；LRU 淘汰后分页；真实过期 409；关停期间不留下加载任务。

## 2B. 查询索引

在 Dataset 构建时建立日期范围与 provider/modelId/familyId 的必要索引；prices 可按常用 provider/modelId 建候选集。先选候选集合，再过滤其他字段，按既有排序输出。

不要为每个字段组合都建立一份全量对象副本。q 子串搜索可先只在候选集内进行；是否引入全文索引由测量决定。weekly 排序可预计算。

将当前扫描实现保留为测试参考，对固定数据集的参数组合做差分验证：实体、顺序、边界日期、limit、nextCursor 解码语义必须一致。验证全部页无重复遗漏、REST/MCP 使用不同 limit 策略但共享同一结果语义。

ETag 仍遵循响应体字节规则；响应体未变化时不能因为缓存或索引实现变化失去 304。记录索引增加的内存与查询节省的时间。

## 2C. 限流分层

先确定客户端额度的唯一执行层。推荐复用 Nginx 按 IP 限流，应用层作为经过容量测量的全局保护；若需要应用层返回精确配额或多种身份额度，再做有界、可过期的客户端桶。

无论选哪种实现，都满足以下要求：

- REST 与 MCP 独立额度；正常总容量下，客户端 A 耗尽自己的额度不影响客户端 B。
- 不把来自反向代理的全部连接都识别成同一个 loopback 客户端。若应用读取客户端 IP，Nginx 必须覆盖相应头，应用仅信任受控代理来源，验证伪造头不能绕过。
- 全局保护是容量上限，不能沿用原来的低共享桶而造成隐藏的共同额度。
- 明确突发容量、补充速率、IPv4/IPv6 标准化、客户端桶 TTL/上限及 NAT 共用 IP 的限制。
- 检查 Nginx 产生的 429 是否满足已有 Problem JSON、Retry-After 和跨域要求；不能只测试直连 Node 的错误形状。
- 不新增 Redis；多实例全局配额留到有实际多实例需求时设计。
