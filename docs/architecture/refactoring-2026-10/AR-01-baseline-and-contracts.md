## 实施步骤

### 1A. 冻结输入与当前事实

记录 commit、工作区状态、Node/Python 版本、CPU/内存、采样日期、数据版本与文件字节数。区分仓库声明、部署验收记录和实际服务器探针；没有做线上检查的字段写 `unverified`。

列出每个服务/组件的职责、输入、输出、启动方式、状态存储、发布方式和故障影响。特别标记 Umami Cloud 与保留的自托管安装脚本，避免将候选脚本当作运行中服务。

### 1B. 核对契约偏差

每项记录：文档说法、代码行为、测试证据、最近决策/验收、处置方式。

至少核对：

- API 文档仍写“不新增 `/models`”，代码已有 `/api/v1/models`：结合 OpenAPI、模型页与验收记录确认当前承诺后修正文档。
- `quality`、时间窗口、modelId/familyId、旧 cursor 的验证与过期规则。
- 当前 REST/MCP 匿名共享桶；AR-02 改变配额作用域时要同步合同。
- README 的 GitHub Pages、待部署描述与当前 release 发布事实。
- 正式周报 Markdown 的部署触发与 site 源文件权威位置。

不要仅因为文档旧就默认代码全部正确，也不要因历史文档的描述而删除已经发布的兼容行为。无法裁定的字段应列成精确待决项，暂停相应改造，其余基线继续完成。

### 1C. 建立性能基线

仅对本地或隔离环境压测。固定输入，预热后至少 3 轮，保存中位数与范围，不以一次结果作结论。

| 类别 | 最少采样内容 |
| --- | --- |
| 数据加载 | 启动加载、同版本重载、新版本加载、历史版本首次加载；耗时、RSS/heap、事件循环延迟 |
| 查询 | changes 日期查询、provider/modelId 筛选、q 搜索、prices 多条件、完整 cursor 翻页；P50/P95/P99 与错误率 |
| 并发 | 并发 1/10/30 的固定负载；分别测查询能力与真实限流行为，报告 429，不能把它算成功响应 |
| 构建 | projection、校验、测试、Astro、API 编译、组装分别耗时；冷依赖安装与热构建分开 |
| 存储 | 目录实际字节/文件数、Git 跟踪数、公开版本数、release 大小；`git count-objects -vH` 单独记录 |

扩展样本使用 1×/5×/10×数据集，在临时目录生成合法 ID、排序、manifest/hash 和证据引用；保留固定随机种子。不能只复制相同 ID 来冒充扩展数据。样本不进入正式归档或站点。

### 1D. 冻结指标预算

在结果中登记目标并注明环境。建议起点：固定本地环境并发 10 下列表查询 P95 ≤ 200 ms、事件循环延迟 P99 ≤ 50 ms；这些是候选目标，不是当前能力承诺。生产资源预算需按实际机器和同机服务分配，不能用开发机结果替代。

无论最终数值如何，“同版本不重新解析业务集合”“分页无重复遗漏”“测试不污染正式产物”是硬验收。若候选数值不适用，记录依据和替代预算，再作为 AR-02/06/08 的正式输入。
