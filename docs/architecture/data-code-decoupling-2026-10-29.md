# 数据与代码发布解耦方案

日期：2026-10-29。状态：已授权实施，生产读取已切换；独立writer和当前Git树脱离验收中，见 [运行记录](data-code-runtime-2026-10-29.md)。

最新约束：用户明确暂不使用对象存储。原文与恢复包使用服务器独立 filesystem 目录，建议 `/srv/maasweekly/shared/data-blobs/`，不在 Git/代码 release 内。PostgreSQL 部署于现有服务器；原文目录和数据库必须分别备份，异地备份目标尚待确定。下文“独立文件存储”均指此方案，不创建云桶或 S3 服务。

## 1. 建议与范围

采用 PostgreSQL 保存可查询的结构化事实、修订、内容和运行状态；独立文件存储保存原始网页、响应、图片及离线导出；Git 保存代码、数据库迁移、采集规则、模型身份定义、契约和小型固定测试样本。

目标是统一数据入口和发布规则，不强求全部字节进入同一个数据库。代码发布与数据发布分别版本化。数据库和独立文件存储独立于应用 release，正常采集不产生 Git commit、不构建全站、不重启应用。

本轮优先迁移公开内容链路。现有账号 SQLite 保持独立，避免把登录、邮件、订阅迁移并入这次性能改造；未来是否并入 PostgreSQL 单列决策。

## 2. 当前证据

2026-10-29 本地工作区盘点：data 约 3.0 GB、约 200,214 个 Git tracked 文件；site/src/data 约 108 MB。data/snapshots 约 1.1 GB、public 约 804 MB、price-facts 约 529 MB、input-manifests 约 110 MB、input-objects 约 97 MB。均为本地 du 舍入结果，不是备份预算或线上容量。

daily-update.yml 当前提交 data/ 和 site/src/data/ 等目录，随后调用统一 release；build-release.sh 运行全量回归，并把整个 site/dist 与 data/public/v1 放入新发布包。10 月 26 日发布记录为约 7.5 万文件、2.38 GB，构建约 17 分钟，其中 regression 阶段约 15 分钟，包含站点构建。

AR-06 已有本地内容寻址适配、迁移清单及恢复演练；远端启用、writer 切换、停止 Git 跟踪尚未完成。可以复用其校验和迁移规则，不把本地演练当成生产已迁移。

## 3. 数据边界与存储选择

| 类别 | 目标权威存储 | 处理规则 |
| --- | --- | --- |
| 来源、实际抓取状态、运行及失败记录 | PostgreSQL | 区分尝试、成功和实际观察时间，失败不改旧事实时间 |
| 来源条目、价格事实、修订、撤回记录 | PostgreSQL | 保留现有 ID；修订追加写入，不能只保存 current |
| 证据元数据、摘录、定位、原文 hash | PostgreSQL | 关联原始对象；可独立查询，不要求每次读取整份原文 |
| 原始网页/响应、图片 | 独立文件存储 | SHA-256 寻址，校验 bytes/hash，保存原始字节及格式 |
| 日摘要、周报、译文与生成来源 | PostgreSQL | 正文可用 text；保留输入引用、模型、prompt hash、状态及审核历史 |
| 正式周报发布稿 | PostgreSQL | 导入时保留已发布正文与 URL；Git 中 Markdown 可作编辑稿，不能与库形成两个自动同步的权威源 |
| 公共数据版本、发布指针、数据合同版本 | PostgreSQL | 可查询、可回退；稳定游标明确绑定数据版本 |
| 旧版公共 JSON、离线下载与恢复包 | 独立文件存储，服务端有界缓存 | 兼容与恢复用途，不随每个代码包重复携带 |
| 代码、schema migration、采集规则、人工维护的身份定义 | Git | 配置变更有 commit；采集到的运行数据不回写这些定义 |
| 小型测试数据 | Git | 脱敏固定样本，不使用完整生产归档充当代码测试依赖 |

PostgreSQL 是面向采集、编辑与服务共同使用数据的目标建议；不是现有 3 GB 数据量已经超过 SQLite 能力。SQLite 能承担单机中小规模网站，若只保留单 writer 且运维成本优先，也可作为方案分支。但本方案不安排先 SQLite 后 PostgreSQL 的两次公开数据迁移。

首期使用普通索引、事务与现有服务，不同时引入 Redis、消息队列、搜索集群或多实例。数据库部署位置、对象桶区域、备份存储与现有机器资源需在实施前核定，不给未经核验的月费或性能承诺。

## 4. 数据版本与原子发布

读者必须看到一份完整数据集，而非一次采集中途的状态。建议流程：

1. 生成 runId，抓取原文并写入不可变对象；取得并核对 hash/bytes。
2. 写入候选事实、证据、摘要和运行状态；用 runId、来源和事实身份保证重试幂等。
3. 在固定输入边界上校验金额与单位、身份、引用闭合、撤回、排序、翻译和来源状态。
4. 生成候选 datasetVersion，执行 API、HTML、RSS 与旧游标的候选冒烟。
5. 以事务比较并切换 publishedDataset 指针，拒绝过期候选覆盖较新已发布数据；同时记录发布审计及待处理缓存失效任务。
6. 发布后按记录更新缓存、RSS、sitemap，并预热主要页面；这些动作幂等重试，旧缓存不会被误标为新数据。

独立文件存储与数据库没有跨系统原子事务：先上传并验证对象，再提交引用。未完成 run 不对外可见；未被引用的对象只在核对完整引用、恢复包与保留期后清理。不能先提交数据库引用再异步补齐原文。

数据库事务快照只能覆盖一次事务，不能替代跨 HTTP 分页的数据版本。事实修订表加发布可见性记录，保存各版本实际选中的修订与列表成员；可采用基线加增量或有效区间，避免每个版本复制整套事实。列表窗口、撤回状态及来源状态也必须按版本固定，不能分页时读取当前表再混用历史 cursor。

迁移同一冻结输入时，保留现有 datasetVersion 的规范摘要算法与 DTO。manifest 的文件路径/hash 作为兼容导出另行验证。后续存储内部主键不替换公开 ID。当前版、7 自然日内版本及至少上一版继续可访问；事实与证据历史的保留不受这条公共快照规则缩短。

## 5. 网页与发布方式

数据迁出 Git 后，如果 Astro 继续枚举所有记录生成静态详情页，构建瓶颈仍会保留。建议保留 Astro 和现有样式，增加 Node 运行适配，把数据页面改为服务端按需渲染并缓存完整 HTML。

| 页面 | 建议方式 |
| --- | --- |
| 关于、方法、稳定指南等低频页面 | 继续预渲染，随代码或编辑发布更新 |
| 首页、动态、价格、榜单、模型列表 | 请求时绑定一个已发布数据版本，SSR + 短缓存；激活时预热 |
| 模型、条目、证据、周报详情 | SSR + 按实体修订缓存；改动实体才失效 |
| REST/MCP/RSS | 同一已发布数据版本；保持既有 DTO、错误语义、ETag 与 cursor 行为 |
| sitemap | 独立数据任务生成索引与分片，不触发 Astro 全站构建 |

HTML 首次返回完整标题、正文、证据与 SEO 标签；不把可索引正文全部改成客户端加载。缓存键包含代码/模板版本、locale、数据或实体修订版本及公开/私有访问边界。一次页面渲染固定读取同一版本；RSS 和首页等关联入口在响应中可核验版本。Plus 周报继续走现有权限校验，私有正文不进入公共缓存或导出。

代码发布：固定 Git SHA → 固定样本全量测试 → 新运行包 → 指定数据版本的真实集成验收 → 蓝绿激活。包内只带程序、模板、静态资源、迁移脚本和兼容性声明，不嵌入整个历史数据集。

数据发布：固定采集代码 SHA → 候选数据及针对性校验 → 原子切换数据版本 → 缓存与入口冒烟。无需 npm build 或全套账户、支付、UI 回归。完整数据扫描按迁移、恢复与定期审计运行；正常批次校验变化数据及其受影响引用，不取消金额、身份、证据和版本一致性门禁。

## 6. 分阶段迁移

| 阶段 | 工作与交付 | 放行条件 |
| --- | --- | --- |
| A：基线与契约冻结 | 分解实际采集/导出/构建/上传耗时；冻结 ID、版本摘要、cursor、ETag、HTML 与访问边界；确认机器/预算和恢复目标 | 有可复现基线和导入清单；没有生产写入变化 |
| B：影子存储 | 对象迁移；固定输入批量导入数据库；旧文件链路继续权威；候选查询与旧 exporter 对账 | 全量实体、修订、引用和原文字节核对；缺失历史原文继续显式标记；真实备份恢复成功 |
| C：独立数据服务与页面 | 新 API 读取适配器、SSR/缓存、独立 RSS/sitemap；数据发布器先演练再切换；开发使用样本或指定数据快照 | 四入口、双语页面、SEO、Plus 权限、历史 cursor、回滚和故障注入通过；至少 7 个正常采集周期影子对账 |
| D：切换权威与停止 Git 数据更新 | 一次性切换 writer 权威到数据库/独立文件存储；旧文件仅作只读对账和恢复；停用每日 data commit；从当前 Git 树移除运行数据 | 多次真实数据发布无代码部署；恢复/回退演练通过后才停止旧路径；保留迁移清单与旧仓库恢复入口 |
| E：历史瘦身 | 检查旧 SHA 构建、链接、恢复与工作流依赖；单独决策归档旧库或重写历史 | 明确旧仓库保留位置和协作者切换步骤；不能把 git rm 当成历史 pack 已缩小 |

避免长期双写：影子阶段单一旧 writer，以冻结批次导入新库；切换后仅新 writer 写权威源。旧文件兼容导出属于可重建产物，不反向回写。每阶段独立评审与排期，A 完成前不承诺总工期。

## 7. 恢复与验收

代码版本、数据库 schema 和数据版本分别记录。数据库采用向前兼容的加法迁移；代码回滚先验证 schema/数据合同兼容性。数据回滚只切换已验证发布指针，后续新事实仍保留；若目标版本缺少已公开 ID，不直接切回，须制作保留这些 ID 的修正版。SSR 模板与缓存回滚按代码版本处理。

Git 退出数据备份职责后，必须在切换前补齐数据库独立备份、对象清单和异地副本；做一次从空环境恢复到可查询版本的演练。具体 RPO/RTO 在 A 阶段确定。外部数据库故障时可保留明确版本的公共缓存或上次成功的兼容快照；无法保证一致的查询返回明确失败，不能用半完成结果或过期数据冒充最新。新存储加入在线依赖后的可用性与容量须实测。

拟定的验收目标（不是当前实测承诺）：

- 正常数据更新产生 0 个 Git 数据 commit，触发 0 次 Astro 全站构建及应用重启。
- 全量 ID、事实修订、原文 hash、金额/单位及稳定游标对账通过；正式周报发布正文保持一致。
- 候选数据完成校验后，发布切换与主要页面预热 P95 目标不超过 60 秒；采集和 LLM 耗时单独计量。
- 代码包体积不随历史记录数量线性增长；冷构建测量与生产数据下载解耦。
- 实际服务器查询延迟、内存、缓存、备份恢复满足 A 阶段冻结的预算；数据库和独立文件存储成本有月度记录。
