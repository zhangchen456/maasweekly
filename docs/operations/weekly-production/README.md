# 正式周报生产与发布

本流程服务 `/weekly/{期末日}/` 和英文入口、公开 API/MCP 周报摘要。独立 `pro_content` 栏目及邮件投递是另一套交付，不因站内周报发布而自动完成。责任执行人是当前承担周报工作的编辑或 Codex；自动任务负责素材整理、结构检查、发布和时效检查，不会自动核实事实或把模板当成成稿。

## 每期节奏（北京时间）

| 时间 | 责任与交付 | 完成标准 |
|---|---|---|
| 周三09:00 | `周报生产流程`自动整理刚结束的周三至周二素材 | GitHub Actions 中产生 `weekly-editorial-packet`，含固定数据版本的完整证据JSON、选题摘要、稿件模板、待填写检查表，保留90天 |
| 周三 | 编辑/Codex筛选3–5个有实际影响的变化并核对原始证据 | 每个事实能追溯观察记录和官方来源；没有可靠变化时不凑数 |
| 周四12:00前（编辑目标时间） | 完成中文稿、英文预览和私有全文译文，审阅后提交PR | 六节结构、四列表格、时间与价格条件正确；检查表绑定稿件SHA256 |
| PR合并后 | 自动正式稿导入；无界面代码变更时不构建网站 | 完整性校验、Linux运行时验收、原子发布和正式期号检查成功 |
| 每天10:00 | `正式周报每日时效检查` | 最新正式期末日年龄不超过10天；缺失、未来期号或API口径不一致会使工作流失败 |

定时任务可能受GitHub排队延迟影响。周四时间是编辑SLA，不代表已有无人值守写作服务。没有完成稿时不会自动出版；失败出现在Actions，通知取决于仓库的GitHub通知设置，不宣称已接入邮件告警。

## 准备与写作

从 Actions 下载本期素材包；也可运行：

```sh
python3 ops/weekly-editorial.py prepare --out /tmp/weekly-packets
# 历史补刊须明确指定已完整结束的周二
python3 ops/weekly-editorial.py prepare --period 2026-10-27 --out /tmp/weekly-backfill
```

API的to是排他边界，工具会自动取期末次日，避免漏掉周二。跨页数据版本变化、分页重复或超出上限均失败，不能把部分数据当完整素材。素材保留完整观察原文；其中LLM摘要不作为独立证据。保留数据版本及覆盖范围，缺测明确记录。

优先写模型/API变化、定价和计费条件、迁移或下线、接入限制与设置。首次抓取、网页导航变化、空报价不直接写成新品或涨价。观察日期与发布日期分开，未来生效项只写预告。金额注明币种、单位、上下文区间和渠道；面向海外的图使用美元。结论说明适用条件，不夸大厂商能力描述。

将完整稿放到 `data/weekly/YYYY-MM-DD.md`，沿用2026-10-27稿件六节结构。平台汇总严格四列：平台、状态、本期重点、核对事项；同一平台合并。补刊在正文可见位置说明实际补刊日期和观察范围。证据必须同时包含站内 `/item/obs_.../` 与官方链接。

英文公开包只放预览与界面文本；付费全文译文进入服务器私有翻译文件，原子更新并保留备份。沿用既有受保护渲染审计确认全文，无待翻译提示且不泄露到公开HTML/JS。不能仅靠动态翻译缓存检查替代私有全文审阅。

## 审阅与发布

复制素材包的 `release.template.json` 至 `docs/weekly-reviews/YYYY-MM-DD.json`。填写实际审阅人、带时区的审阅时间、证据数据版本、全部引用观察ID及稿件SHA256；只有实际核对后才将五个检查项置为true。此回执是编辑记录，工具不替代事实判断。

```sh
python3 ops/weekly-editorial.py check \
  --draft data/weekly/YYYY-MM-DD.md \
  --receipt docs/weekly-reviews/YYYY-MM-DD.json
```

PR检查覆盖所有修改的稿件和回执；改稿后旧哈希失效。发布客户端再次检查最新稿及已有回执的稿件，然后才连接生产。更早的未变历史稿沿用既有发布记录，不伪造追溯审阅；改动历史稿时必须补对应回执。稿件和回执一起提交PR，合并后观察“线上更新”中的import-weekly任务。

手动重新导入在“周报素材与正式稿发布”选择import。aggregate只收集素材并验证候选，不发布；full保留需要同时收集来源和更新滚动摘要时的完整流程。常规正式稿发布用import。

## 发布后验收与失败处理

检查最新API期号、数据版本、中文和英文页面、Plus门槛、匿名全文401及内部全文路由404；确认MCP期号一致。记录工作流链接、代码版本、数据版本、期号、耗时及失败项。私有全文译文仍需真实服务端审计；页面HTTP成功不能代替视觉或邮件验收。

导入失败时旧公开版本保持不变。若出现pending journal，先保留journal、固定输入版本和`/work/formal-drafts/<sha256>.json`；按现有恢复工具恢复/丢弃，不删除标记后强跑。正式稿在journal内部注入，恢复先还原上一完整输入，再重放同一哈希稿件请求。后续数据库提交和公开原子切换维持原机制。

已合并但内容不合格时提交修订稿和更新回执后重新导入；数据错误按既有数据发布回退流程处理，不能仅回退代码。邮件只对真实已授权订阅者按原有规则单独交付，不发伪造测试收件。

## 耗时诊断

writer日志新增`writer.timing`，包括各脚本、ingest.capture、ingest.raw_manifest、ingest.raw_copy和ingest.database。正式import不再重跑滚动摘要；零缺失翻译只读检查；稿件入journal后复用已提交baseline；已有原始对象通过不跟随符号链接的文件描述符读取并验证哈希。仍执行全文输入捕获、归档/证据校验、数据库提交、运行时验收和原子发布。

以服务器writer开始至候选完成的时间比较，另记GitHub排队和部署时间；不能把排队缩短算成处理性能提升。首次恢复缓存、不同数据量或其他并行任务会影响耗时，保留测试条件。

缓存恢复仅枚举可修改输入，避免扫描约20万份历史归档来恢复少量当前文件；原始归档不在恢复动作的写入范围。完整capture、归档门禁和discard仍覆盖历史文件。新增initialize计时用于区分缓存恢复与正式导入耗时。

入库阶段的历史对象验证统一在事务提交前执行：每个唯一哈希只读取一次，并同时检查原始字节、长度、数据库JSON和字段顺序；未变对象也全量验证，任何失败都回滚本次SQL写入。先核对数据库解析清单与固定输入完全一致，再在同一事务复用该清单；不跨任务缓存验证结果。同一哈希出现不同长度会报错，避免去重掩盖错误。JSON不支持字符检测保持原有NUL/代理字符边界，改为正则扫描并对每个对象只算一次。新增database.resolve_parent、write_deltas、resolve_committed_view、verify_all计时。
