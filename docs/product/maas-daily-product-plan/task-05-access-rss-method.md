# Task 05：Agent 接入页、RSS 与方法说明

状态：待实现，可直接交给 coding agent 执行。日期：2026-09-16。

前置：Task 01–03 已形成稳定条目、价格证据和统一公开数据投影；Task 04
已完成 MCP、五个只读工具和可安装 Skill 的本地实现及 Claude Code 验证。
Task 04 的 Codex 真实客户端验收仍待具备 OpenAI 认证环境后补完，因此本任务
不得把 Codex 写入“已验证支持”列表。

本任务完成 P0 的公开接入入口：用户可以在一个页面选择 Skill、MCP、RSS 或
REST API，复制准确配置，理解数据范围和方法，并订阅两个稳定 feed。本任务只
完成本地实现与可审查验证；生产 API/MCP 路由、服务托管、缓存头、统一部署和
回滚属于 Task 06。

## 1. 目标与用户体验

用户从 `/agent/` 出发，不需要账户或本站 API Key，即可：

1. 看懂四种接入方式分别适合什么场景，以及当前是否已经上线、经过哪些真实
   客户端验证。
2. 复制 Skill 安装、MCP 配置、RSS 地址或 REST API 示例，并得到明确的成功
   反馈和无 JavaScript 时的手动复制方式。
3. 用一个验证问题完成首次查询；成功标准是拿到真实数据、版本、数据截至时间
   和覆盖范围，不是只完成下载或保存配置。
4. 订阅最近变化或正式周报；条目更新时身份稳定，链接回到永久详情页。
5. 从 `/method/` 理解观察时间、证据完整性、价格条件、修订与撤回、陈旧数据
   和 LLM 摘要限制，不把本站结果理解成实时官网或完整发布记录。
6. 从 `/changelog/` 了解公开接口范围和兼容策略，不依赖虚构的历史或弃用公告。

## 4. 单一公开配置

新增一个可由页面、feed、测试和 `llms.txt` 构建脚本共同读取的配置来源，至少
包含：

- canonical site URL，以及 `/agent/`、`/method/`、`/changelog/`、OpenAPI、
  MCP、Skill manifest／installer、两个 feed 的相对路径。
- REST、MCP、Skill 和 RSS 的公开状态：`available`、`pending` 或 `unavailable`，
  以及可向用户展示的简短原因。
- 已验证客户端的名称、精确版本、验证日期和传输方式；待验证项单独存放。
- API/MCP/Skill 合同版本。不得在多个页面手写可能分叉的域名或版本。

构建应拒绝 `localhost`、`file://`、本机绝对路径、空生产域名和未知状态值进入
公开产物。配置中的 `pending` 是真实产品状态，不应导致构建失败。

## 5. `/agent/` 接入页合同

页面按以下顺序组织：能问什么、四种接入方式、配置／安装、验证问题、成功
示例、数据范围与更新节奏、故障恢复与反馈。四种接入方式为：

| 方式 | 面向用户 | 必须提供 |
| --- | --- | --- |
| Skill | 希望 Agent 自动选择查询方法的用户 | manifest、installer、显式 `--dir` 示例、更新／卸载、真实验证问题 |
| MCP | 支持 Streamable HTTP MCP 的客户端 | `/api/mcp`、已验证客户端配置、版本、当前上线状态 |
| RSS | 阅读器与低频自动化 | 两个 feed、内容差异、建议 30 分钟或更慢轮询、修订语义 |
| REST API | 开发者和脚本 | base URL、OpenAPI、最小 curl 示例、分页与错误合同 |

具体规则：

- 每段可复制内容旁有明确按钮、成功／失败反馈和 `aria-live`；Clipboard API
  不可用时保留可选择文本，不显示虚假“已复制”。
- 配置片段不包含密钥、用户 home 路径或机器信息。Skill 命令不使用 sudo，
  `--dir` 使用明显占位符，并解释必须由用户选择实际目录。
- MCP 只展示真实验证通过客户端的完整配置。待验证客户端可以列出状态和解除
  条件，但不提供“已支持”徽标。
- 示例回答必须来自当前公开 release，包含 datasetVersion、dataThrough、实际
  coverage 和永久链接；构建时不把某个易变化模型或价格写死为产品承诺。
- 页面明确说明本站数据是观察快照、不代表实时官网；无结果只表示当前覆盖内
  未记录匹配项。
- 四张接入卡在 320px 和 375px 宽度下可读；代码块横向滚动，不撑破页面；
  键盘可操作，焦点样式可见。
- 在主导航或页脚加入接入页入口，并从接入页链接方法说明和变更记录。不要让
  新入口挤压现有移动导航。

## 6. RSS v1 合同

### 6.1 两个 feed

- `GET /feed.xml`：当前公开 release 中最近的有效变化，最多 100 条，顺序必须
  与公开 changes 查询的默认排序一致。
- `GET /feed/weekly.xml`：最近 30 期以内的正式周报，不混入滚动摘要、草稿或
  自动生成但未正式发布的内容。
- 两者输出 RSS 2.0、UTF-8 和正确 XML content type；feed 自身及每个 item 都
  使用 canonical HTTPS URL。
- feed 元数据中的更新时间来自所包含数据或 release 的 `dataThrough`，不能把
  站点构建时间冒充数据时间。

### 6.2 身份、链接和修订

- 变化项 GUID 使用稳定 record ID；周报 GUID 使用稳定 weekly ID。GUID 不得
  包含 datasetVersion、标题、排序位置或构建日期。
- 变化链接指向 `/item/{id}/`，周报链接指向 `/weekly/{id}/`；构建后必须在
  `dist` 中真实存在，不能只做字符串格式检查。
- 同一记录修订时保持 GUID，更新标题／摘要／状态。阅读器是否覆盖旧条目取决
  于客户端，因此 feed 和页面都应提示详情页是修订与撤回的权威状态。
- 已撤回记录不作为新的“有效变化”继续进入默认 feed；已经被阅读器缓存的
  内容无法可靠召回。不得用新 GUID 制造一条假“新变化”来覆盖旧项。

### 6.3 时间与内容

- 有精确观察时间时可输出 `pubDate`。只有日期精度的记录不得合成午夜时间；
  RSS item 的 `pubDate` 可省略，并在描述中保留原始日期精度。
- 描述只包含本站编写的摘要、必要状态和来源链接，不复制第三方页面全文或长
  摘录。来源原文应通过 evidence／官方 URL 回查。
- XML、HTML 和 URL 全部转义；恶意标题、CDATA 终止符、控制字符、脚本标签
  和超长内容不得破坏 feed 或产生可执行 HTML。
- 相同 release 重复构建时 feed 业务内容必须逐字节稳定；不得写入随机值、当前
  时钟或临时路径。

### 6.4 缓存边界

Task 05 负责生成稳定静态文件，并在合同中建议 `Cache-Control` 至少 30 分钟、
支持 ETag/304。真实响应头和条件请求由 Task 06 的生产服务器配置验收；本任务
不得因为本地静态文件可解析就宣称线上缓存已生效。

## 7. `/method/` 方法说明合同

方法页必须与当前 schema、归档和公开合同一致，至少解释：

1. 页面文本 diff、截断、重新计算和噪声边界；来源页变化不等于供应商正式
   发布、下线或调价。
2. 首次观察时间、来源发布时间、价格事实观察范围、dataThrough 和站点构建
   时间的区别。首页与价格页继续显示各自数据时间，不能用 build time 替代。
3. evidence 的完整／部分／未知状态，以及摘要、定位和官方来源各自能证明什么。
4. LLM 摘要可能出错，稳定 ID、结构化事实、证据和官方页面如何逐层核验。
5. 价格币种、单位、计费组件、区域、档位、billing mode 和附加条件；不做跨
   单位、跨条件的自动“最低价”结论。
6. leaderboard、汇率或人工维护数据的边界和更新时间；未知值明确显示未知。
7. 抓取成功、价格解析通过和最后有效事实时间是三种不同健康信号；stale、
   partial、unknown、unavailable 的含义和失败沿用策略。
8. 修订与撤回、RSS 缓存限制、详情页／API 作为最新状态来源。

易变化的数量和覆盖范围应从当前公开 release 渲染；不能把当日数字写死在正文。
若项目尚未确定数据再分发许可或反馈地址，页面应使用经产品确认的中性说明或
显式待补状态，不得用代码许可证替代数据许可，也不得编造邮箱。

## 8. `/changelog/` 与 `llms.txt`

- changelog 是人工维护的公开接口变更记录。首条真实记录说明 API v1、MCP、
  Skill、RSS 和网页入口的实际状态与已知限制，不倒填不存在的发布日期。
- v1 内允许增加可选字段、端点说明和兼容能力；删除字段、改义、改稳定 ID 或
  改默认排序属于破坏性变更，应新开 v2。
- 只有确定的停止日期和迁移路径才能发布 `Deprecation`／`Sunset`；不要为了
  “完整”写虚构公告。
- `llms.txt` 只提供站点用途、数据快照声明和正式入口链接，不复制整份合同、
  不嵌入实时数量、不宣称待验证客户端兼容。

## 9. 失败与恢复

- 当前公开 release、manifest 或被引用文件缺失、hash 不符、版本不一致时，
  构建必须失败，不能生成空 feed 或显示“当前没有变化”。
- 单条记录违反 RSS 合同时，构建应报告稳定 ID 和规则，但不输出本机绝对路径、
  原始恶意文本或 secret。
- 复制 API 失败时保留文本和键盘选择方式；页面主体不依赖 JavaScript 才可读。
- 未上线的端点显示 `pending` 原因和预计由 Task 06 完成的动作，不提供会失败的
  “立即验证成功”流程。
- Task 04 Codex 验收若仍未完成，Task 05 结果文档继续列为阻断项；不能通过
  删除客户端名称、改成笼统“兼容 MCP”或只跑协议测试来关闭。

## 10. 开发顺序

1. **基线复核**：确认当前 release、线上域名、Task 04 实际兼容状态、现有导航
   和移动布局，记录不可硬编码的动态字段。
2. **共享配置**：建立端点、状态和客户端验证唯一来源；先写漂移与本地路径门禁。
3. **RSS**：定义合同并实现两个 feed；完成身份、排序、时间精度、转义、修订和
   永久链接测试。
4. **接入页**：实现四种方式、CopyBlock、真实状态、验证问题和失败恢复。
5. **方法与变更页**：对照 schema 和合同逐条核实措辞；生成精简 `llms.txt`。
6. **站点整合**：增加导航／页脚入口，完成桌面、320px、375px、键盘和无 JS
   检查，不改现有页面主体。
7. **端到端验收**：构建 `dist` 后解析 feed、遍历链接，并用本地预览走一遍接入
   流程和标准 RSS 阅读器／解析器导入。
8. **交付收尾**：写 `task-05-result.md`，更新 README、HANDOFF 和本目录索引，
   清理临时文件；不部署、不提交无关改动。
