## 2. R2 [P1] sync 并未使用全量预检流程

代码：`pipeline/scripts/sync-diff-to-site.py:135–139`、`:157–163`。

实际逻辑仍是逐文件循环：

```text
读取文件
  JSON 损坏 → continue
  校验这个文件 → 计划这个文件 → 立即 apply_plan
读取下一个文件
```

虽然公共模块已有 `plan_and_apply`，sync 入口没有调用它，而是在循环内调用 `load_and_validate_diff / plan_records / apply_plan`。所以“两个入口先全部校验再写”的交付结论与代码不符。

### 独立复现 A：损坏文件仍被忽略

临时工程放入：

- `2026-09-11.json`：一个正常已注册来源的 changed。
- `2026-09-10.json`：内容 `{broken`。

执行实际 sync.main（只把路径指向临时工程）：返回成功，归档 1 条。损坏文件被第 138 行捕获后跳过，没有进入新增校验函数。

### 独立复现 B：报错前已经写入

先有 09-11 的正常归档。修改该日的变化内容；09-10 放入未映射来源。

执行 sync：退出 1，但比较前后 records 文件字节，**已发生变化**。此时 stderr 仍声称“未写入任何内容”。

### 修复条件

1. sync 的全部日期、已有归档及计划先完成检查，之后才进入任何归档／站点写入。
2. 不保留坏文件 `continue`；输入错误必须硬失败。
3. 复用公共计划入口，或让公共函数返回完整计划由 sync 应用；不要在逐文件循环里 apply。
4. 测试必须执行实际 sync 入口，不只调用公共 `plan_and_apply`。

复验用例：正常更新放在前面，错误放在后面；分别测试坏 JSON、未映射来源、同源冲突。断言退出非零且 records、revisions、daily、weekly、index 全部字节不变。

## 3. R3 [P1] 恢复只处理“当前文件缺失”，漏掉真实更新中断

代码：`pipeline/scripts/record_archive.py:214–223`、`:286–290`、`:315–324`。

新增恢复函数遇到当前记录存在就直接返回。更新时使用原子替换，中断通常留下旧当前版本，不会删除它。因此“删当前文件再恢复”的测试不能代表正常更新中断。

### 独立复现

1. 创建完整 r1：当前记录 r1、修订 r1 都存在。
2. 修改摘要，执行 merge 准备写 r2。
3. 注入失败：允许修订 r2 写入；在 `_atomic_write(records/<id>.json, ...)` 抛出 OSError，模拟替换当前文件前中断。
4. 此时当前仍 r1，历史已有 r2。
5. 等待超过 1 秒，以完全相同业务输入重跑 merge。

结果：恢复函数因当前 r1 存在而跳过；merge 重新生成 r2 的 revisedAt，和已写 r2 内容不同，报“修订版本文件已存在且内容不同”。归档校验报告“孤立修订（版本超过当前 revision 1）”。

这不是新增需求，而是第一轮 R3 已要求的“处理中断可恢复重跑”。

### 修复条件

1. 定义并处理两种状态：当前缺失；当前落后于已完整写入的修订。
2. 恢复前验证修订的连续性、身份和内容，不能简单信任任意高版本文件。
3. 同一业务操作重试应复用已落盘版本及其修订时间，不重新制造冲突。
4. 对不可信的冲突仍拒绝覆盖，不能为恢复而删除历史。
5. 如果采用事务标记／日志，应在入口恢复阶段处理后再全量校验，避免预检将合法中断状态永久锁死。

复验用例：在“修订成功、当前替换前”故障注入，保留旧当前文件，间隔后从真实归档入口重跑；预期恢复一致、没有多余修订、校验通过。另测首次创建与撤回的相同故障点。
