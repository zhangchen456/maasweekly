## 阻断问题

### P1：在线同日重跑使用了错误的日基线

`pipeline/scripts/fetch-prices.py` 的 `_baseline_before()` 以目标日次日 00:00（上海时区）为截止点，因此会把目标日已经写入的版本选为基线。若同一天价格依次为 `10 → 8 → 9`，第二次变化会被记录为 `8 → 9`，而任务约定要求同一日始终与前一日固定基线 `10` 比较，即 `10 → 9`。

这会使价格事件详情与兼容的 `daily_changes` 口径分叉，也会在价格当日回到旧值时产生错误事件。

验收要求：截止点改为目标日开始时刻；增加真实入口级用例，覆盖同日 `10 → 8 → 9`、回到 `10` 和重复执行。

### P1：归档契约错误会被当作抓取失败吞掉并继续提交

在线入口在每个来源内立即写快照、证据和事实版本，且使用宽泛的 `except Exception` 将不可变文件冲突、归档损坏等 `ArchiveError` 也降级为“抓取失败，沿用上轮”。随后程序仍会写 ledger、history、run、current、事件和索引。

这违反了任务要求的归档预检和失败零写入契约。若后处理在某个较晚来源才发现冲突，前面来源的文件已经落盘；若在 ledger/history 之后、run/current/events 之前中断，还会留下跨产物不一致。

验收要求：归档契约错误必须直接失败；写入前完成全量预检或使用可恢复的提交协议；增加“后一个来源冲突”和各提交阶段中断的入口级测试，验证退出码非零且业务状态可恢复到一致状态。

### P1：`complete` 不能证明证据支持对应事实

`assess_evidence_completeness()` 只检查整段摘录中是否出现任意金额和任意单位，未核对当前事实的模型、计费组件、金额、单位及必要条件；`conditions` 参数也未参与判断。同一张大表中的任意金额和单位，可能让所有引用该表的事实都被标记为 `complete`。

因此，结果文档中的“完整证据 100% 已验证”目前无法成立。它只能说明摘录看起来像价格内容，不能说明每一条价格事实可由该摘录独立复核。

验收要求：将完整性判定绑定到具体事实，至少验证模型、组件、金额、单位和适用条件；对共享大表建立事实到行或单元格的明确定位；用错金额、错模型、缺条件和共享表串证据用例验证不会误判为完整。

## 重要问题

### P2：构建证据页时重复扫描全量事实版本

`site/src/pages/evidence/[id].astro` 为每一个证据页重新读取并解析全部事实版本。当前 2,365 个证据页、约 8,600 个事实版本已经形成数千万次文件判断和 JSON 解析；实测单个证据路由约需 185–205 ms，完整构建耗时达到分钟级，并随数据增长近似二次恶化。

验收要求：构建前一次性建立 `evidence_id → facts` 索引，通过 `getStaticPaths` props 或生成索引传入页面；以当前数据量记录优化前后完整构建时间，并设置可执行的构建时限。

### P2：构建门禁仍有一致性盲区

当前校验只遍历 `1..current.revision`，不会发现高于 current 的额外修订文件；证据仅复算 `excerptHash`，未从快照 ID、定位器、摘录哈希和提取器版本重算证据 ID；也没有核对证据与快照元数据的内容关联。`current` 只验证版本引用存在，未验证 fact key 对应关系和是否指向该事实最新已接受版本；run 记录未纳入提交状态和引用校验。

验收要求：补齐上述双向和内容寻址校验，并为额外修订、证据 ID 篡改、快照错链、current 错键/倒退、prepared run 残留分别增加门禁失败用例。

### P2：证据页显示“未知时间”

证据记录没有 `observedAt`，但证据索引和页面标题直接读取该字段，因此摘录标题显示“未知时间 保存”。关联事实中已有观察时间，页面应使用明确的证据采集时间，或删除无法兑现的时间标签。
