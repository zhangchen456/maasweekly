# 后台运营系统规划

日期：2026-10-04。版本：0.0.1。状态：规划建议，未实施。

## 目标与假设

让维护者每天从一个入口判断：用户是否获得价值、内容是否按时且可靠地交付、系统哪里需要处理。首版按一位维护者兼任运营、编辑和开发设计，保留多人分工能力；不先建设复杂组织审批。

核心工作流：发现异常或待办 → 查看关联证据 → 执行动作 → 验证结果 → 留下处理记录。后台首页优先显示待处理事项，趋势指标辅助判断。

## 当前依据

- 账号已有登录、资料、模型关注、偏好、会话撤销与数据导出，复用现有私有 SQLite。
- Plus 已有公测权益、手工授权与使用事件。公测激活不是付款，手工授权也不是订单。
- 反馈已有提交、私有截图、用户查询和维护者 CLI；当前对用户状态为待处理、处理中、已解决。
- 专业内容已有草稿、审核、出版、撤回、组合与投递能力，后台应复用这些业务规则。
- 仓库已有 Umami 部署与站点统计相关实现。接入后台前核对实际可用指标和访问权限，本规划未读取实时流量。
- 以 2026-10-04 统一上线记录为当前发布依据；较早文档中的“生产未发布”为历史记录。代码发布不代表专业样例已审核出版。

依据：[统一上线](../../operations/all-local-release-2026-10-04/README.md)、[账号](../account-system-v2/README.md)、[订阅](../subscription-v1/README.md)、[反馈](../product-feedback-v1/README.md)、[专业内容规范](../maas-pro-briefing-v1/content-spec.md)、[专业运营规则](../maas-pro-briefing-v1/operations.md)。以下新增能力均为建议，不代表已存在。

## 模块与优先级

P0 为首期闭环，P1 为运营稳定后扩展，P2 为商业化阶段。

| 模块 | 首期 P0 | 后续 |
| --- | --- | --- |
| 运营总览 | 待审核周报、失败任务、未处理反馈、数据新鲜度、用户与内容使用摘要；点击进入处理对象 | P1 自定义异常阈值、按负责人聚合 |
| 用户管理 | 按邮箱/ID检索；账号资料、权益来源/期限、关注数量、邮件偏好、反馈及使用摘要；授权/撤销权益、撤销会话 | P1 停用与恢复账号、分群、数据删除流程 |
| 流量与使用 | 接入现有流量汇总；来源、热门页面、注册、公测激活、周报阅读、Agent调用；独立展示采集健康 | P1 留存、渠道转化、内容间比较 |
| 内容与周报 | 素材池、选题、生成、证据审核、预览、出版、更正与撤回 | P1 专题库、个人范围组合、选题效果复盘 |
| 增值服务 | Free/Plus 状态、公测与手工授权、到期、权益审计、专业凭证撤销 | P2 付费订阅、订单、退款、对账 |
| 任务与投递 | 抓取、摘要、周报、邮件等任务运行记录；失败原因、阶段重试、耗时与模型用量；收件结果 | P1 可配置调度、预算告警与自动恢复 |
| 反馈与问题 | 反馈队列、私有截图、内部排查记录、公开处理说明、关联修复与发布验证 | P1 相似问题归并、辅助诊断与修复候选 |
| 数据与信源 | 来源最近成功时间、采集失败、证据缺失、异常价格、重复事件的处理队列 | P1 信源配置编辑、噪声规则与覆盖分析 |
| 系统与审计 | 服务状态、当前发布版本、备份结果、后台访问控制、关键操作日志 | P1 恢复演练记录、更多运营角色 |

导航建议：总览 / 用户 / 流量 / 内容 / 增值服务 / 任务 / 反馈 / 数据质量 / 系统。首版页面可合并，但对象应可互相跳转，例如反馈 → 用户 → 对应内容 → 修复版本。

## 用户与权益

用户详情以“该用户当前能否正常使用”为中心，展示账号状态、权益判定结果及原因、订阅偏好、最近反馈和必要业务事件。匿名统计不能强行归因到个人；没有埋点的数据明确为空。

授权和撤销必须记录操作者、原因、起止时间和前后值。公测、手工授权、未来付费订阅分别记录来源。运营不能替用户开启邮件；撤销登录会话不等于撤销专业 API 凭证，两类动作分别呈现。密码、验证码、令牌明文不进入后台。

后续停用账号必须明确是否同时影响登录、API/MCP、RSS、邮件和既有权益；首版不以删除用户记录替代停用。

## 流量与指标

将网站访问、账号行为、Agent/API 使用和系统可靠性分开展示。统一支持近7天、近28天、自定义时间；默认北京时间，并显示数据截至时间。采集失败显示不可用，不能显示为零。

| 指标 | 口径与来源 |
| --- | --- |
| 网站访问 | Umami 提供的访问量、访客、来源及页面；沿用其口径，不称为注册用户数 |
| 注册用户 | 时间窗内新建账号数，来自账号库 |
| 公测激活率 | 同一注册队列中7天内激活公测人数 / 已满7天观察期的注册人数；未成熟队列单列 |
| Plus 阅读覆盖 | 周期内有效Plus用户中至少成功读取一期全文的人数 / 周期内至少有一次有效权益的用户数；按 user_id 去重 |
| 内容价值 | 各期去重读者、回访、导出、反馈；成功读取不等于读完，不虚构阅读完成率 |
| 4周回访 | 首次专业阅读队列在第4周再次产生专业阅读的人数 / 已满4周观察期的队列人数 |
| 邮件交付 | 入队、供应商接受、送达、失败、未知分别计数；供应商接受不等于送达 |
| 内容成本 | 每期所有生成与审核尝试的模型费用、耗时、人工审核时间；估算金额标注依据 |
| 反馈处理 | 首次人工响应时间、上线验证后的解决时间、积压时长，优先看中位数和P90 |

运营负责解释业务指标，维护者负责采集完整性。上线后先积累两周基线，再设转化与留存目标，不预设无依据的增长数字。现有事件不足时补埋点，历史不可还原部分不回填猜测值。

## 每周高质量周报

每期报告是有版本、证据、负责人和截止时间的交付物；任务运行只是生产它的过程。同一期重试可以有多个运行记录，不能产生多次出版或重复邮件。

建议流程：

1. 固定统计窗口与数据版本：沿用专业简报 `[上周一00:00，本周一00:00)` 北京时间，保存来源覆盖与缺失情况。
2. 整理素材：规则与较低成本模型去重、归类、关联模型及平台；人工可剔除噪声、补充线索。
3. 选题：按实际影响、证据可靠度、读者相关性筛选重点，记录入选理由。数量随事实变化，不为凑数制造变化。
4. 深度分析：独立配置高能力模型及推理预算，分析跨平台关系、历史变化、适用对象和需核对的事项。
5. 核验：程序验证证据、日期、数值与比较条件；独立模型审稿检查事实跳跃、矛盾与遗漏。模型审稿不能替代证据验证。
6. 人工审核：同屏查看正文、来源和问题清单；可以修改、退回、重跑单段或允许出版。正文修改后原审核失效。
7. 出版与投递：冻结正文及公开预览，记录版本，通过已有权限与出版规则提供内容；按用户独立邮件偏好投递。
8. 复盘与更正：记录读者反馈、编辑修改量、成本；事实错误关联所有引用报告，并沿用修订/撤回流程。

内容结构沿用既有规范：本周重点、重要变化详解、历史或跨平台比较、适用条件、待核对事项、覆盖限制与证据。公共事实和付费分析分别投影，预览不可泄露全文。

模型角色配置为“素材整理 / 深度分析 / 审稿”，均保存供应商、模型标识、提示词版本、输入证据版本、参数、用量、费用与耗时。模型具体选择留到真实样例评测；本规划不指定尚未验证的“最强”型号。用户资料和反馈截图不作为常规周报输入。

质量放行条件：关键事实均可追溯；价格比较口径一致；结论与事实区分；未解决冲突不写成确定结论；缺失覆盖明确披露；人工审核完成。评价强模型时使用同一批历史素材，对比事实错误、遗漏、分析价值、人工修改时间及总成本，而非只看文笔。

任务支持阶段保存、超时、有限重试、取消和预算上限。模型不可用时保留草稿并提示延期，未经核验的降级稿不自动出版。没有重要变化与采集失败分别处理。周一整理、周二发布可作为候选节奏，尚不配置定时任务。

兼容事项：现有 compose 首次冻结范围，未入队的同周期报告不能靠重跑补发；后台必须如实显示这一限制。若需要补发，应另行实现明确的补发任务及去重规则。投递结果未知的任务先核对供应商，不直接重置后重发。

## 反馈排查与修复

内部流程建议：待分诊 → 排查中 → 待修复 → 待发布 → 待验证 → 已解决；另设待用户补充、重复、非缺陷。首版保持对用户现有三态：待分诊对应待处理，其余未完成阶段对应处理中，验证通过后才映射已解决。内部备注与公开处理说明使用不同字段。

反馈详情包含现有描述、路径、私有截图，补充优先级、影响范围、负责人、复现结果、相关内容/任务/请求标识、修复提交或PR、上线版本、验证结果。日志关联仅使用实际取得的标识，不能声称能追溯未采集的历史现场。

代码问题进入修复与发布流程；内容问题进入编辑更正流程；数据问题进入信源/事实修正流程。重复反馈链接到同一问题，原用户仍可查看处理进度。

后续 AI 可整理问题、建议复现步骤、分析已脱敏日志并生成修复候选。首版不提供后台任意执行命令或一键让模型直接改生产。修复沿用现有测试、不可变发布和上线验证；以线上验证结果作为解决依据。默认沿用用户在“我的反馈”查看说明，不新增自动外发消息。

## 任务、数据质量与系统

任务详情保存类型、触发方式、计划时间、开始/结束、运行阶段、关联对象、输入/输出版本、错误分类、尝试次数和成本。后台首期只提供预定义动作，如生成草稿、阶段重试、更新反馈、出版内容；每种动作调用服务端业务能力。

区分“任务进程完成”“数据有效”“内容可出版”“邮件已送达”。信源连续失败、覆盖下降、证据缺失或价格异常进入待办，不能因抓取进程退出码为0而判定正常。

系统页展示当前发布版本、数据版本、服务健康、备份时间与最近恢复演练结果；能备份和能恢复是两个状态。后台不另造发布通道，引用现有发布与验收记录。

管理员资格由服务端独立授予，普通账号和Plus账号均无后台权限。首版一位管理员，但数据模型保留操作者身份；私有页面和接口不缓存。反馈图片读取需新增经过验证的管理员权限路径，不能复用仅允许提交者访问的接口冒充用户。

关键写入校验来源与权限，防重复执行和过期版本覆盖，记录操作者、时间、对象、原因、前后值与关联任务。审计不记录凭据或不必要的个人信息。模型密钥通过服务端配置管理，后台只显示配置是否可用。

## 实施顺序与验收

| 阶段 | 可交付结果 | 放行标准 |
| --- | --- | --- |
| A：统一运营入口 | 管理员权限、总览、用户权益、反馈队列、流量摘要、任务与健康只读视图 | 普通用户无法访问管理数据；管理员可定位用户问题并更新公开说明，操作可追溯；不可用数据明确显示 |
| B：周报生产闭环 | 素材与证据、模型任务、编辑审核、出版、投递状态、费用记录 | 使用一批真实历史素材完成一次隔离演练；未审核不能出版；同一期重复触发不重复出版/投递；失败可从阶段恢复 |
| C：稳定运营 | 信源异常处理、反馈关联修复版本、内容更正、邮件失败处置、留存分析 | 反馈可追溯至线上验证；内容修订能定位受影响报告；未知投递不盲目重发；指标口径可复算 |
| D：收费运营 | 支付、订阅、退款、对账及服务成本 | 独立方案明确账单来源与支付状态，再启用；公测和手工权益不能计入收入 |

首版不包含复杂营销自动化、通用工作流编辑器、多租户管理，也不默认每个用户生成一份全新长文。优先用已审核内容按用户关注范围组合，便于控制质量和成本。

首期验收目标：一位维护者可在总览发现并完成一个反馈处理流程；可从真实素材完成一份有证据且经审核的周报；能准确区分失败、未知和完成；所有权益、出版和反馈状态变更可追溯。效率改善以上线前人工操作记录为基线验证。

## 后续需确定的运营参数

这些参数不阻碍当前规划，但在排期和启用自动任务前需要确定：

- 维护者确认每周出版日、审核负责人及可投入时间；暂用人工触发，自动生成仅到草稿。
- 维护者确认每期模型费用上限；暂采用按次限额、预算耗尽暂停，不无限重试。
- 维护者确认是否近期收费；默认继续现有免费公测，首期不接支付。
- 实施时核对 Umami 接入、业务事件覆盖和专业定时任务实际配置；缺少集成时先展示明确状态及现有管理入口。

本次仅新增规划文档，没有开发后台、调用模型生产正式内容、改动调度或部署。
